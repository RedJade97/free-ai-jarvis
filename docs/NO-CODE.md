# The same second-brain workflow without code

Use a text editor and private folders. An existing assistant can help, but you can perform the steps yourself. This route has no automatic calculations, duplicate prevention or lifecycle enforcement: you must check those manually. It does not require a paid voice agent, editor, connector or database service.

## 1. Make your private notebook

Create a folder named `My Second Brain` outside any public repository. Inside it, create `inbox`, `sources`, `experiments`, `lessons` and `weekly-reviews`. Copy the memory template into the top level. Keep sensitive information out of public forks and shared links.

## 2. Capture evidence with a receipt

For each source, save its file or URL and write a dated note containing an ID, origin, relevant excerpt or observation, and what is missing. For metrics, keep the source screenshot/export and observation timestamp. Do not replace yesterday's measurement with today's.

Use [EVIDENCE.md](../templates/EVIDENCE.md). A memory that says "this opening works" is not enough; you need the content, the result and the context in which it happened.

## 3. Plan one comparison

Copy [EXPERIMENT.md](../templates/EXPERIMENT.md). Give the experiment a unique ID. Write your objective, the property being tested, what remains similar, the observation age and success rule **before** inspecting the results.

Use one concept with control and test variants for an initial comparison. Assign each a distinct post or output ID. Two cuts of one concept remain one concept when evaluating a general lesson.

## 4. Collect comparable results

Measure at similar ages and keep different platforms and distribution periods separate. For content, pair saves and views from the same observation:

`saves per 1,000 views = 1,000 × saves ÷ views`

If views are zero or either count is unknown, mark the result unknown. Do not manufacture a retention value between sparse observed points. Keep transcript, screen descriptions and original-to-cut time maps alongside the metrics. See [the content walkthrough](CONTENT-WORKFLOW.md).

## 5. Review with your assistant or by hand

Supply only the relevant evidence, memory and [review procedure](../procedures/02-review.md). Ask for measured differences, alternative explanations, counterexamples and specific next changes. An assistant needs the actual media to assess it; a filename is not access.

Save the review under the experiment ID. Record progress as planned, testing, reviewed and closed. Only close when the actual decision has been recorded. Create a new linked experiment for the next test.

## 6. Store a lesson as a claim you can challenge

Copy [LESSON.md](../templates/LESSON.md). Write one claim, its scope, its supporting and opposing evidence IDs, a repeatable test recipe and the conditions that would weaken it. Start with **hunch**. Keep the original wording when later evidence contradicts it.

## 7. Test it against new evidence

Collect later independent concepts, not renamed copies or more snapshots of the same posts. Apply the recorded rule to every eligible item, including failures. Keep the eligible-ID list, exclusions, calculation and outcome. Do not count the same evidence twice.

Use the [learning rules](LEARNING-RULES.md) as a bookkeeping convention, with the same limitations. If calculations become difficult, use the local tool in [SETUP.md](../SETUP.md), which checks them reproducibly without an AI subscription.

## 8. Review weekly and carry knowledge forward

Use [WEEKLY-REVIEW.md](../templates/WEEKLY-REVIEW.md). List which lessons strengthened, weakened, contradicted or became stale. Choose at most three next tests. When starting a new assistant chat, provide your current memory, the relevant lesson notes and their evidence. Do not depend on hidden chat memory to preserve the archive.

Back up the private folder. Voice is optional presentation; the durable asset is your traceable collection of evidence, decisions, procedures and revisable lessons.
